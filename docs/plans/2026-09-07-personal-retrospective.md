# 下一期迭代计划：有证据的个人阶段回顾

- 日期：2026-09-07
- 依据：本次 grill-me 访谈中用户逐项确认的产品决策，以及本机 Codex / Claude Code Session 的只读结构核对。
- 状态：产品方向与验收标准已对齐；下文开发切片为实施建议，尚未实现。
- 与现行规范的关系：本文件记录下一期方向，不将现行 PRD v0.3 或真实数据大考改记为已升级、已通过。模型能力落地时应同步更新 PRD、相关 ADR 与 AGENTS.md 的适用范围。

## 1. 这一期要证明什么

> 用户用自己的会话生成一份有个人辨识度的阶段回顾，并主动保存它。

回顾以几段具体的关键经历为核心，呈现当时的问题、重要选择和后续进展，保留用户自己的原话。结果有依据才写，无法确定的地方留白。

用户的明确选择与方向变化优先成为候选线索，再关联执行结果说明后续进展。采用第一人称、克制的个人叙述；感受和意义来自用户明确表达或补充的内容。

## 2. 已确认的产品决策

| 项目 | 决策 |
| --- | --- |
| 当前价值目标 | 生成用户能认出、愿意保存的个人阶段回顾 |
| 内容单位 | 几段关键经历：问题、选择、进展、原话与出处 |
| 选段优先级 | 明确选择、方向变化优先，执行结果补充进展 |
| 叙述口吻 | 第一人称；生成叙述与逐字引用分开呈现 |
| 模型角色 | 筛选片段、组织经历、生成带出处的候选草稿 |
| 人工环节 | 保存前检查准备留下的 3～5 段经历，可保留、修改、移除 |
| 核对负担 | 3～5 分钟为设计目标；正式验收上限为 5 分钟 |
| 信任状态 | 模型解释是待确认草稿；用户认可后记录为“本人确认”，不升格为系统 verified |
| 模型调用 | 一期接受用户配置云端模型，由用户主动发起生成；界面说明模型与处理范围 |
| 生成前敏感确认 | 一期不额外增加敏感信息确认步骤；后续离线版本再单独讨论相关边界 |
| 分享导出 | 继续执行静态 HTML 导出前的敏感信息检查；生成与分享是两个操作环节 |
| 范围与选展 | 沿用产品现有范围选择与选展方式；撤回新增“单项目＋时间段”硬限制的建议 |
| UI | 必须美观；视觉对标由用户寻找，视觉验收单独进行 |
| 首轮价值验收 | 用用户本人的真实数据，按第 6 节三项标准验收 |

用户明确同意下一期调整当前“不引入模型”的范围约定。保存前的叙事核对也属于新增产品环节，不应直接复活已删除的旧核对队列、合并拆分工具或人工展签代码。

“3～5 段”是目标规模，不是填充配额。以下为实施建议：材料不足时说明不足，允许少于目标数量，避免为凑数生成经历。

## 3. 本轮实际核对结果

### 3.1 样本与限制

- Codex：检查 8 份历史用户 Session 文件，共 1,864 行，约 16.4 MB；包括 5 份 DigitalMuseum 文件及 3 份较近样本，排除当前访谈文件及非用户线程。
- 其中包含续接文件，8 份文件不等于 8 次独立会话；不能按文件名直接累计独立会话数。
- Claude Code：检查本机 `~/.claude/projects` 下当时可见的全部 11 份 JSONL，共 327 行。
- 本轮只读解析源文件并调用现有扫描函数，没有执行档案导入、同步或数据库写入。
- 结论描述本次样本，不宣称覆盖所有产品版本或用户数据。

### 3.2 Codex：2026-09-07 核对时扫描器与实际消息格式失配

2026-09-14 已实施本节 Codex 兼容修复，支持、去重和未覆盖边界见 [会话读取兼容性说明](2026-09-14-codex-session-compatibility.md)。下面保留当时的复现记录；真实档案库未在本轮全量重同步。

真实样本的发言位于 `event_msg.payload.type = item_completed`，其 `item.type` 为 `UserMessage` 或 `AgentMessage`；同时存在 `response_item.message` 记录。

样本中可识别 14 条 `UserMessage` 和 54 条 `AgentMessage`。正文在两种记录中有重叠，不应相加计数；`response_item` 的 user 容器还可能包含注入上下文。

当时分类器只识别旧式 `event_msg.user_message / agent_message`。直接调用 `scan_session_file(path, _classify_record)` 时，这 8 份文件均返回有效摘要，但 `user_messages = 0`、`assistant_messages = 0`、`first_user_message = None`。

因此，先修格式兼容是本次实施建议的首要依赖。这个结果不代表现有数据库已全部出错，也不代表修复已经完成。

样本还包含：

- `CommandExecution`：命令、执行目录、状态、标准输出、标准错误、退出码等；可以支撑当次执行结果的表述。
- `FileChange`、`McpToolCall` 等其他操作记录；具体状态含义需要按类型处理。
- `session_meta.history_base`、`compacted.replacement_history` 等续接或压缩信息；不能把一个文件假设为完整、无重复的全部历史。
- `response_item` 的工具调用和返回可通过 `call_id` 关联；输出实际既可能是文本，也可能是内容块数组。

### 3.3 Claude Code：需要识别系统包装和回复分块

正文位于 `message.content`，实际既有字符串，也有内容块数组。记录包含 `uuid`、`parentUuid`、`sessionId` 等定位与关系字段。

- 67 条顶层 user 记录中，排除 `isMeta` 与 XML 包装后剩 29 条文本候选；候选数不等于已确认真实用户发言数。
- 43 条 assistant 记录中有 16 条 API 错误消息。
- 同一 `message.id` 可分布在多行；不能仅凭重复 ID 丢弃整行，需要保留不同内容块。
- 观察到 `server_tool_use` 与 `tool_result`，通过调用 ID 关联；本批没有覆盖完整的本机命令执行闭环。
- DigitalMuseum 的 Claude 文件仅 12 行，足以验证部分结构，不足以验收项目转折叙事。

这意味着可以统一回顾材料的接口，但不能把未观察到的 Claude 工具、分支、压缩格式记为已验收。

### 3.4 现有档案还不是多轮叙事材料包

当前适配器保存首尾时间、计数和首问摘要。首问先折叠空白，在派生证据文档中截取 120 字，在 claim 中进一步截取 60 字。现有锚点指向生成的统计文档，不是源 JSONL 中任意一条完整消息。

此外，现有同步会替换旧 occurrence 及其引用，并可能回收旧 blob。保存的回顾如果直接依附可被替换的引用，后续复核可能失去原文。

下一期需要完整原话的提取与定位，以及固定保存入选证据片段的能力。采用已有内容寻址机制，并为回顾保留独立、有效的引用；具体表结构在实施时确定。

## 4. 建议的使用流程

```text
同步与浏览现有档案
    ↓
沿用现有范围选择与选展方式
    ↓
用户主动生成回顾
    ↓
系统整理所选范围的对话材料与相关执行结果
    ↓
模型生成带原文出处的第一人称草稿
    ↓
用户核对准备留下的 3～5 段经历
    ↓
保存本人确认的回顾及其证据片段
    ↓
导出静态 HTML 时执行敏感信息检查
```

材料解析与模型生成可以先验证内容质量；用户提供视觉对标后，再结合真实草稿完善页面。

## 5. 开发切片与出口条件（实施建议）

| 顺序 | 工作 | 完成条件 |
| --- | --- | --- |
| 1. 真实格式兼容 | 支持本次观察到的 Codex 消息结构，保留旧格式；处理 Claude 文本、系统包装、错误与分块 | 去标识化样本中的真实发言可正确提取；旧格式回归通过；包装不算用户发言、分块不误丢、重复不累计；无法识别的格式不冒充已核实的零消息 |
| 2. 回顾证据材料 | 整理多轮用户/助手正文，关联相关执行结果，保留消息时间、源记录位置和完整原话 | 任一引用能逐字匹配提取时保存的片段；能区分提出、决定、助手报告、实际执行与结果；时间范围、续接与压缩缺口有明确处理 |
| 3. 模型草稿 | 接入一个用户配置的模型接口，按选择与转折优先组织第一人称经历 | 先在真实材料上生成可查看出处的候选草稿；引用 ID 有效、引用文字可机械比对；事实关系与个人意义仍留给核对，不以机械检查代替判断 |
| 4. 核对与保存 | 支持保留、修改、移除，保存本人确认版本及固定的证据引用 | 后续同步、源文件追加、重新生成均不覆盖已确认的回顾与原文证据；模型稿、用户修改与逐字原话可区分 |
| 5. 展览与导出 | 将已确认回顾接入现有展览与静态导出，依据视觉对标完善 UI | 新增模型回顾内容经本人确认后才导出；现有确定性档案沿用原导出规则。保持无脚本、自包含 HTML，新增叙事和引用同样纳入导出敏感检查，浏览和导出内容一致 |
| 6. 真实价值验收 | 用预先封存的经历清单做盲测，再核对、保存 | 满足下一节三项标准，人工判定有记录；视觉验收单独记录 |

实现时按既有分层、样式和测试约定推进。源 Session 只读；转录中的历史指令只作为材料，不应由回顾生成链路执行。

补充的实现边界：

- 范围选择仍使用已有交互；读取材料时以消息时间和出处解释范围，不能直接将整条会话开始日当作所有消息发生日。
- 只统计用户主线程的既有口径继续适用；不因引入叙事而自动混入子代理审计记录。
- 普通“好的、继续”仅在能明确关联具体取舍时构成决策候选，不把操作确认都写成转折。
- 压缩摘要可作寻找材料的线索，不作为用户逐字原话。缺失的原始历史应显式留空。
- 原话快照保留原字词、换行及标点；展示或检索用文本与原文分开，用户编辑叙述不改写原始证据。
- 工具结果只能说明对应执行在当时的结果；不自动证明任务全面完成、成果已发布或当前仍然有效。
- 生成异常、取消或重试应保留此前已确认版本，避免重复触发未说明的模型请求。

## 6. 用户已认可的验收标准

### A. 能找回重要经历

验收前，用户先列出所选范围内 3 件想留下的经历，独立封存。模型生成时不能看到这份清单，也不能把其内容放入生成提示词。完成初稿后再逐项对照，至少找回 2 件。

“找回”由用户判断，不能仅凭项目名称或关键词重合判定。清单预写是验收动作，不加入每次日常生成流程。

### B. 内容有据可查

每段会话来源的叙述能查看对应原文，明确区分提出、决定、执行和结果；没有证据的部分留白。用户新增的感受或解释标明为本人补充，不伪造会话出处。

### C. 核对负担可接受，并实际保存

从首次看到生成草稿开始，到完成核对并保存为止，用户能在 5 分钟内完成。模型等待时间另记，不混入人工核对时间。验收需记录实际保存行为及用户是否愿意留下这份回顾。

### 验收记录表

| 项目 | 填写内容 |
| --- | --- |
| 材料范围与提取版本 | 待验收时填写 |
| 经历清单封存时间 | 待验收时填写 |
| 生成使用的模型与版本 | 待验收时填写 |
| 3 件经历分别是否找回 | 待用户判定 |
| 逐段证据核对结果 | 待用户判定，机械引用检查作为辅助 |
| 人工核对耗时 | 待实测 |
| 保存产物 | 待实际生成，记录本地文件或回顾标识 |
| 是否愿意留下 | 待用户判定 |
| UI 对标及视觉验收 | 对标由用户提供；待验收 |

这次单用户验收不替代 v0.3 的历史大考判定，也不代表已经完成外部用户验证或证明市场需求。

## 7. 实施前需要落实的少量事项

- 用户提供 UI 对标；在此之前可以验证解析、证据和草稿质量，不能宣称视觉已验收。
- 确定首个模型接口及其配置方式，验证请求长度、耗时、费用预算和超限处理；本次未选定供应商、模型或具体预算，也未实际调用新的模型接口。
- 选定首轮真实验收材料并封存经历清单；Claude 暂缺的执行证据格式需要补样本验证。
- 开始相应实现时同步更新 PRD、相关 ADR 与 AGENTS.md，明确模型草稿和叙事核对的新范围。保留现行真实性契约、单用户、本地档案及静态导出边界。

Skill 机会发现、完全离线模型版本、新输入来源、云部署和多用户不纳入本次建议实施切片。它们如有需求另立迭代，不作为本期成功的前提。

后续建议：本人验收通过后再安排小范围外部试用；本次没有确定试用人数、招募方式或执行时间。
